# Архитектура — «ПОСЛЕДНИЙ ИСТОЧНИК: Waifu Uprising»

Документ описывает архитектуру вертикального среза (Этап 1) и систем Этапа 2
(прогрессия, магазин, архетипы врагов, навигация, разрушаемость); решения рассчитаны
на масштабирование до полной игры (8 классов, 3 акта, 1–8 игроков, dedicated-сервер).

## 1. Слои системы

```
┌─────────────────────────────────────────────────────────────┐
│ UI (main_menu, hud)          — только чтение состояния,     │
│                                команды через Net/Game       │
├─────────────────────────────────────────────────────────────┤
│ Поток матча (Game, MatchController, WaveManager)            │
│   фазы LOADING→COUNTDOWN→FIGHT→VICTORY|DEFEAT — на сервере  │
├─────────────────────────────────────────────────────────────┤
│ Боевые единицы (PlayerPawn, EnemyFop, GigaChad)             │
│   FSM + симуляция движения — только на сервере              │
│   компоненты: Health / Hitbox / Hurtbox / Knockback         │
├─────────────────────────────────────────────────────────────┤
│ Сеть (Net autoload, BodySync, MultiplayerSpawner)           │
│   ENet, лобби-RPC, снапшот-репликация, валидация команд     │
├─────────────────────────────────────────────────────────────┤
│ Данные (ClassDefinition, EnemyDefinition, WaveDefinition)   │
│   .tres-ресурсы — баланс и контент без правки кода          │
└─────────────────────────────────────────────────────────────┘
```

## 2. Сетевая модель (ТЗ §16)

**Server-authoritative.** Сервер (peer 1 — listen-хост, либо dedicated headless):
- симулирует движение и FSM всех пешек/врагов/NPC;
- активирует хитбоксы и считает попадания, урон, отбрасывание;
- владеет здоровьем, волнами, статистикой и исходом матча.

**Клиент:**
- сэмплирует ввод (60 Гц) и шлёт `sv_input(seq, move, aim_yaw)` — `unreliable_ordered`;
- действия (удар/рывок) — отдельным `sv_request_action` — `reliable` (гарантия доставки);
- применяет снапшоты мира через `BodySync` с интерполяцией (задержка ~120 мс).

**Валидация RPC:** `sv_input`/`sv_request_action` принимаются только от `owner_peer`
пешки; вектор движения ограничивается `limit_length(1.0)`; лобби-RPC проверяют
состояние и лимиты (имя санитизируется, класс сверяется с реестром, поздний
вход в матч отклоняется).

**Репликация — собственный компонент `BodySync`** (вместо MultiplayerSynchronizer):
- сервер каждые 50 мс шлёт снапшот `{p, y, v, s, hp, ...}` (unreliable_ordered);
- клиент держит буфер снапшотов и интерполирует непрерывные поля
  (позиция/рыскание/скорость) по render-time = now − 120 мс;
  дискретные поля (состояние FSM, здоровье) берутся из актуального снапшота;
- одинаковый протокол для игрока, врага и Гигачада — новые сущности
  подключаются реализацией `get_sync_payload()/apply_sync_payload()`.
- Этап 7: дельта-сжатие, релевантность по расстоянию/обзору, адаптивный rate.

**Спавн — `MultiplayerSpawner` c `spawn_function`:** сервер вызывает
`spawner.spawn(data)`, где `data` — сериализуемый словарь (id класса, путь
EnemyDefinition, позиция). Функция спавна исполняется на всех пирах и собирает
узел из тех же сцен — имена узлов совпадают, RPC-пути стабильны.

**Handshake загрузки сцены:** после `sv_start_match` каждый пир грузит арену и
шлёт `cl_scene_ready` (с ретраями — защищает от гонки «пакет раньше узла»);
сервер начинает отсчёт, когда готовы все (или по таймауту 15 с).

**Offline = частный случай сервера.** `Net.is_server()` истинно без ENet-пира,
все `rpc()` с `call_local` исполняются локально — одиночная игра и тесты идут
по тому же коду, что и сеть.

## 3. Бой и физика (ТЗ §13)

- Компоненты: `HealthComponent` (урон только на сервере, репликация значения),
  `HitboxComponent` (Area3D, активация на время окна удара, «одно попадание за
  взмах», фильтр по командам), `HurtboxComponent` (приёмник урона единицы),
  `KnockbackComponent` (импульс отбрасывания с экспоненциальным затуханием).
- **Скорость тела = управляемая составляющая + knockback** (композиция, а не
  накопление) — удар отбрасывает врага на ~1 м, серии ударов толкают дальше.
- Слои физики: 1 world · 2 player · 3 enemy · 4 gigachad · 5 hitbox_hero ·
  6 hitbox_enemy · 7 hurtbox_hero · 8 hurtbox_enemy. Враги сталкиваются друг
  с другом (mask включает слой 3) — требование «враги сталкиваются».
- Телеграф атаки врага: фаза WINDUP (0.55 с) — поза поклона + золотое мигание
  цилиндра + звук; прерывание WINDUP ударом игрока → HITSTUN.
- Вес попадания: отбрасывание + hit-flash + damage numbers + тряска камеры +
  звук (процедурный, `Sfx`). Hit-stop через `Engine.time_scale` сознательно НЕ
  используется в мультиплеере (влияет на серверную симуляцию); запланирован
  локальный «freeze» анимации жертвы на Этапе 7.

## 4. Поток матча

1. Меню → хост создаёт комнату (ENet, порт настраивается, до 8 игроков) /
   клиент подключается по IP. Лобби: имя, класс, ready, список игроков.
2. Хост жмёт «Начать матч» → `sv_start_match(scene, seed, snapshot игроков)`.
3. Арена: handshake загрузки → сервер спавнит пешки по данным лобби →
   отсчёт 3.5 с → `WaveManager` спавнит волну (`count_base + count_per_player×N`).
4. Победа: все волны зачищены. Поражение: здоровье Гигачада = 0.
   Результат, статистика (убийства/урон/падения) — reliable RPC всем пирам.
5. «Ещё раз» (хост) — ре-матч тем же составом с новым seed; «В меню» — разрыв.
6. Отключение игрока в матче: сервер удаляет его пешку, матч продолжается
   (ТЗ §4 «падение одного не завершает матч»).

**Гигачад:** защищаемый объект (600 HP) + генератор резонанса (+4/с). При 100
резонанса — авторазряд «Волна Резонанса»: лечение героинь в радиусе 9 м и
отбрасывание врагов (реальная механика энергии из ТЗ §5; траты игроками —
Этапы 2–3). Смерть Гигачада → поражение.

**Игрок (Берсерка):** 120 HP, молот (26 урона, отбрасывание 9), рывок с
i-frames, падение → возрождение от источника через 5 с с 60% HP.

## 8. Прогрессия и экономика (Этап 2)

**ProgressionSystem** (узел арены, сервер) — единственный авторитет XP/уровней/
улучшений/валюты/покупок. Клиентские RPC (`cl_choose`, `cl_buy`, `cl_wave_ready`)
валидируют отправителя (`get_remote_sender_id() == владелец состояния`), фазу матча,
баланс, лимиты и актуальность предложения. Клиент получает только зеркало
собственного состояния (`cl_prog`, событийно — не каждый кадр) и целевые RPC
(оффер/тост/результат покупки).

- **XP**: вклад по урону (`_contrib` на каждого врага), награда начисляется РОВНО
  один раз за смерть (guard `rewards_granted` + очистка вклада). Формула уровня
  `xp_base + xp_per_level × (L−1)` — в `ProgressionBalance` (.tres). Остаток XP
  сохраняется при нескольких уровнях подряд; на max_level начисление останавливается.
- **Улучшения**: 12 `UpgradeDefinition` (.tres): эффект (enum), значение, макс.
  уровень, редкость, цель (SELF / GIGACHAD — командные резонансные). Сервер
  считает модификаторы (`compute_mods`) и применяет к пешке:
  `apply_progression()` пересчитывает эффективные статы (`st`), НЕ мутируя общий
  `ClassDefinition`. Командные улучшения накапливаются на Гигачаде.
- **Оффер**: 3 уникальных допустимых улучшения из пула (server RNG от match_seed —
  воспроизводимо), серверный таймер `choice_time`; по истечении — автовыбор первого.
  Одновременные выборы разных игроков независимы; повторный RPC не дублирует эффект
  (состояние `offer_active` сбрасывается до применения).
- **Магазин**: 5 `ShopItemDefinition` (.tres) с эффектами (мгновенное лечение,
  временный бафф урона — тикает только в фазе FIGHT, постоянная защита, +макс.HP,
  вампиризм за убийство). Валидация: фаза INTERMISSION, цена, баланс (никогда не
  уходит в минус), лимиты за интермиссию и за матч. Покупки атомарны: списание и
  учёт лимитов до применения эффекта.

## 9. Межволновой цикл (Этап 2)

Единый state machine матча (MatchController), без конкурирующих машин:

```
LOADING → COUNTDOWN → FIGHT ─(волна зачищена)→ WAVE_COMPLETE ─(2.5 с)→
INTERMISSION(магазин, ready, ≤30 с) → COUNTDOWN(5 с) → FIGHT(следующая волна) …
FIGHT(последняя волна зачищена) → VICTORY;  Гигачад пал → DEFEAT
```

- Волны: 4 `WaveDefinition` (.tres) c группами `WaveGroup{def, base, per_player}`;
  волна 1 сохраняет формулу Этапа 1 (3+2N Пижонов). Очередь спавна — детерминированное
  перемешивание групп от match_seed; лимит одновременных врагов `max_alive`.
- Победа/поражение объявляются ровно один раз (guard по фазе); `stop_waves()`
  прекращает спавн и гасит очередь при завершении матча; снаряды удаляются
  (`call_group("projectiles","expire_now")`).
- В интермиссию поверженные игроки воскрешаются (50% HP); награда за волну —
  только живым на момент зачистки.

## 10. Архетипы врагов (Этап 2)

`EnemyBase` (scripts/ai/enemy_ai.gd) — общая FSM (SPAWN/CHASE/WINDUP/STRIKE/
RECOVER/HITSTUN/DEAD), движение «управление + knockback», анти-застревание,
синхронизация, урон/смерть/награды. Архетипы = данные (.tres) + тонкие подклассы:

| Архетип | Данные | Поведенческий код |
|---|---|---|
| Пижон | базовые параметры | базовая FSM |
| Громила (элит, 50 XP) | HP 180, скорость 2.8, урон 30, KB 14, масса 2.6, `recover_damage_mult=2.0` | уязвимость в RECOVER через `health.incoming_damage_multiplier` (база) |
| Тень | HP 40, скорость 6.5, серия `attack_hits=3×0.16 с`, урон 6 | `_chase_move`: рывки (dash) конечной длительности с cooldown |
| Плевальщик | HP 50, `ranged=true`, `keep_distance=9`, `min_distance=5.5`, снаряд 15 м/с | `_chase_move`: удержание/отход/стрейф; `_begin_strike`: серверный снаряд |

**Снаряды** (`SpitProjectile`): создаются ТОЛЬКО сервером через MultiplayerSpawner
(клиент не может породить авторитетный снаряд), прямолинейный полёт, попадания
по XZ-дистанции до героев, удаление по попаданию/таймауту/границе/концу матча,
глобальный лимит 16 одновременных (арена), репликация — тот же BodySync.

## 11. Навигация (Этап 2)

- `NavigationRegion3D` на арене, source geometry — группа `nav_source`
  (пол/стены/колонны/ящики, статические коллайдеры, mask=1).
- Bake выполняется РАНТАЙМОМ на сервере (`bake_navigation_mesh(false)` +
  `map_force_update`) — воспроизводимо в headless, editor-bake не требуется.
  Клиентам навигация отключена (ИИ серверный) — экономия CPU.
- Каждый враг имеет `NavigationAgent3D` (только сервер): цель обновляется каждый
  кадр движения, `_nav_move_dir()` возвращает направление к следующей точке пути;
  fallback на прямое движение при отсутствии агента/маршрута/достижимости;
  анти-застревание сохранено как защитный механизм.
- Разрушение ящика: объект يخرج из `nav_source`, сервер дебаунсит и перепекает
  mesh (0.4 с) — проходимость обновляется; перепекание не чаще необходимого.

## 12. Разрушаемые объекты (Этап 2)

`DestructibleProp` (StaticBody3D): серверное HealthComponent, 2 визуальные стадии
повреждений до разрушения, разрушение фиксируется один раз (guard), событийные RPC
(`fx_stage`, `fx_destroy`) вместо пер-кадровой синхронизации, коллизия и видимость
снимаются сервером (объект «не воскресает»), обломки — локальные RigidBody на
каждом пире (6 шт., 2.2 с, автоочистка таймером — без сетевого трафика), награда
(XP+монеты) через `destroyed_by` → ProgressionSystem (однократно), абстракция
пригодна для колонн/дверей (те же компоненты).


## 13. Классы и эволюции (Этап 3)

**8 классов × 3 формы = 24 `ClassDefinition`** в `resources/classes/` — данные,
не код. Боевая логика едина (`PlayerPawn`); дублирующих классов нет.

- **Реестр `Classes`**: `definitions`/`order` — только базовые формы I;
  `all_by_id` — все 24; `get_form_chain(base_id)` → [I, II, III] из
  `evolution_chain` базы; `is_selectable(id)` — форма I с `implemented=true`
  (валидация лобби `_sv_set_class` и список меню). Заглушки классов из очереди
  разработки (`implemented=false`) в лобби не появляются — статусы в
  `docs/CLASS_MATRIX.md`.
- **Форма = данные**: статы, трейты, `unlock_level`, визуальные параметры и
  слот `model_scene` (PackedScene — туда в Inspector назначается импортированный
  `.glb`; процедурная заглушка тогда не строится).
- **Эволюция (сервер-авторитет)**: `ProgressionSystem.add_xp` → `_check_evolution`
  → `PlayerPawn.try_evolve_for_level(level)` — идемпотентный цикл по цепочке
  (порог `unlock_level`, возможен скачок на 2 формы). `_apply_form`: подмена
  `class_def` + `refresh_effective_stats()` (HP НЕ сбрасывается: при росте
  максимума долечивается дельта — как у iron_body), перестройка визуала,
  подпись «• II/III», `fx_evolve` RPC (кольца/звук/анонс на всех пирах —
  коротко, без кат-сцены), `Events.unit_evolved`. Узел пешки не пересоздаётся:
  позиция, cooldown, улучшения, owner_peer и сетевой путь спавнера сохраняются.
- **Репликация формы**: поле `"f"` в снапшоте BodySync. Клиент при изменении
  вызывает `_set_form_replicated` — меняются ТОЛЬКО визуал/подпись/class_def-ссылка;
  статы и бой клиент не пересчитывает (авторитет сервера).
- **Трейты форм (данные → хуки)**: комбо-ударная волна (`shockwave_*`: каждый
  N-й подтверждённый удар — серверный радиальный урон/отбрасывание через штатную
  damage-pipeline с учётом XP-вклада; форма III бьёт и по `destructibles` —
  «разрушает укрытия»); добивание (`execute_*` в HitboxComponent: ×mult цели с
  HP-долей ≤ порога); неистовство (`frenzy_*`: при собственных HP < порога —
  множители урона/темп атаки поверх прогрессии, откат при восстановлении).
  Все поля нейтральны по умолчанию — классы без трейтов играют базовый комплект.
- **Визуальный слой изолирован**: `player_visuals.gd` — только косметика
  (`rebuild(def)` пересоздаёт `ModelRoot`); бой/физика/сеть живут в компонентах
  пешки и rebuild их не касается. 24 заглушки параметризованы (оружие/причёска/
  цвета/свечение/масштаб), форма III — аура-кольцо и парящие осколки.
- **Гонки смены сцены**: все серверные RPC-обработчики сценных узлов и новые
  эволюционные пути (shockwave/evolve) защищены `is_inside_tree()` — пакет,
  достигший узла вне дерева во время реванша/выхода в меню, игнорируется.

### 13.1. Умения и парирование (Этап 3.1, Валькирия)

- **Единый вход действий**: `sv_request_action("attack"|"dodge"|"skill"|"parry")`
  (reliable, валидация sender==owner) — новых RPC не добавлялось; ввод:
  действия `skill` (E/ПКМ) и `parry` (F) в project.godot (существующие
  привязки не изменены). Клиент лишь просит — все проверки и эффекты на сервере.
- **State.SKILL** (6-е состояние FSM пешки) — рывок: `_ctrl_vel` через
  move_and_slide (стены останавливают естественно), в середине рывка ОДИН
  радиальный проход `_server_shockwave` (общий с Берсеркой механизм: штатная
  damage-pipeline, attacker_peer → XP-вклад/статистика/награды).
- **Парирование**: `try_parry()` открывает серверное окно (`parry_window`);
  хук `try_parry_hit(damage)` вызывается из `HurtboxComponent.receive_hit` и
  `SpitProjectile._hit_hero` ДО нанесения урона — успех полностью отменяет урон
  и выдаёт: защитный бонус (`incoming_damage_multiplier × parry_guard_mult`
  на время; складывается с прогрессией в `refresh_effective_stats`), усиление
  следующей атаки (`_empower_mult`, ровно один взмах), контратаку
  (`_parry_counter`: радиальный урон, форма III — со стаггером). Окно
  расходуется однократно — повторные попадания бонус не дублируют; cooldown
  ограничивает спам. Хук нейтрален для классов без парирования (метод есть
  у всех пешек, но `parry_window=0` → всегда false).
- **Зеркальные копии (форма III)**: НЕ отдельные сущности — серверная очередь
  `_phantom_queue` эхо-ударов (лимит 4, таймеры тикают в `_server_sim`,
  смерть пешки очищает очередь). Эхо наносит урон через `_server_shockwave`
  и НЕ вызывает `on_hit_landed` → рекурсия копий и дубли наград исключены.
  Визуал — локальные полупрозрачные силуэты (`VisualFx.phantom_slash`, группа
  `phantom_fx`, время жизни ~0.5 с, автоочистка tween-ом).
- **Цепной удар (форма III)**: `_do_chain_attack` — один раз за взмах
  (`_chain_done_this_swing`), от позиции первичной цели, N ближайших врагов
  вне дуги взмаха; урон цепочки также не вызывает `on_hit_landed`.
- **Дополнительный удар комбо (форма II)**: повторная короткая активация
  хитбокса в фазе восстановления (`combo_extra_strikes`); hit_once_per_activation
  сбрасывается на каждую активацию — та же цель легально получает оба удара.
- **Дальность ближней атаки**: `melee_range_scale` из данных формы множит
  масштаб hitbox-сферы вместе с `range_mult` улучшений (общий clamp 0.5–2.2).
